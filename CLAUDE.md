# newton-liu.com

Photography portfolio for Newton Liu — birds, wildlife, landscape. Static
site, no build step, no dependencies. Deployed by pushing to `main`
(GitHub Pages serves the repo root). The photographs themselves are not in git:
they are served from Cloudflare R2 (see "Where the photographs live").

## The one rule

**Content is data. Never hand-write a photograph into HTML.**

Photos live in `data/photos.json`, generated by `tools/build.py`. Collections
live in `data/collections.json`, hand-edited. Prose lives in `data/text.json`.
`assets/site.js` renders the first two, `assets/edit.js` applies the third.
Adding 200 photos should change zero lines of HTML.

## Layout

```
index.html                  landing page — the globe and the collections list
work.html                   the same collections as a grid of covers ("Index")
about.html, contact.html    prose pages
collections/<slug>/index.html   one stub per collection (generated; ~15 lines)
assets/site.css             ALL styling — design tokens in :root at the top
assets/site.js              renders the grid, the collection cards, the lightbox
assets/globe.css, globe.js  the globe landing only (see "The globe" below)
assets/edit.js              the words layer — applies data/text.json, and
                            turns the page editable when the URL says ?edit
data/collections.json       hand-edited: trip titles, blurbs, order, covers
data/places.json            hand-edited: where each collection sits on the globe
data/photos.json            GENERATED — do not hand-edit structure, but
                            hand-edited text fields are preserved on rebuild
data/text.json              every word on the site that isn't a photograph's;
                            overrides the copy written in the HTML
tools/build.py              scans images/, writes photos.json, makes thumbs
tools/upload.py             puts the photographs in Cloudflare R2, proves they're there
tools/hooks/                refuse image files in git, and data ahead of R2 (pre-commit, pre-merge-commit)
images/<slug>/*.jpg         the photographs, one folder per collection  (not in git: R2)
images/_thumbs/<edge>/      generated smaller widths                    (not in git: R2)
images/_about/              the About page's images — the one image folder in git
```

Folders under `images/` starting with `_` are skipped by the scanner.

## The globe (landing page)

The home page is a dark globe that turns slowly, with a pin wherever a
collection was photographed and the list of collections on the left (below
the globe on a phone). Pointing at a row or a pin lights that collection;
clicking flies there, lifts the terrain, and opens a card with the
collection's opening photograph and a link into the gallery. A second click
on the same row, or the card, opens the gallery. Keyboard and screen-reader
users get the rows as plain links. `work.html` ("Index") shows the same
collections as a grid of covers, rendered by site.js's `renderHome`.

**Adding a collection to the globe is one entry in `data/places.json`**,
keyed by the collection's slug, after the usual collections.json entry:

```json
"peru": {
  "status": "draft",
  "where": "",
  "pins": [
    { "name": "Lima", "lat": -12.05, "lng": -77.04 },
    { "name": "Sacred Valley", "lat": -13.31, "lng": -72.12 }
  ]
}
```

- **Region level only.** A pin is a national park, island, reserve, valley
  or town a visitor would recognise, at that public place's usual centre.
  Never a photograph's own GPS position, and never a nest, roost, lek or hide.
- `pins` are in route order: they set the line drawn between them, and the
  first is the one the globe turns to. One pin per place; a collection that
  covers several places (The Canadian West) gets several, and they light up,
  fly and frame together.
- `where` is the short line under the title in the list and the card; `""`
  hides it. `zoom` (optional, single-pin only) sets how close the camera
  arrives. `sensitive: true` keeps it back at zoom 7 (the sage-grouse leks).
- `status` is `"draft"` until Newton has confirmed the row.
- A collection with no entry is still listed; it just has no pin.

Overlapping pins of different collections merge on screen into one ringed
pin; clicking it zooms in until they separate. At the overview only each
collection's first pin shows, so the globe stays calm as collections are
added.

**The map is the site's one outside library**, on the landing page only:
MapLibre GL JS (pinned, loaded from jsDelivr as a module in index.html),
with free, keyless map data from OpenFreeMap (coastlines, borders, park
outlines) and Mapterhorn (elevation for the relief and 3D terrain). The map
style is written in globe.js (`buildStyle()`), not loaded, so it stays
greyscale and English-only. **Their credit line is required by their
licences and must stay visible** — restyle it, never hide it. If the
library or the data fail to load, or the device has no WebGL2, the list
still works on its own; under Save-Data the globe waits for "Load globe".

globe.js reads photographs only through `window.NLSite` (exported by
site.js: `url`, `responsive`, `collectionDate`, `aspectOf`, `getJSON`), so
the landing resolves image URLs exactly as the galleries do. No photograph
is requested until a row or pin is pointed at. Every label globe.js puts on
the page is in `LABELS` at its top; the numbers (spin speed, zooms, timings)
and switches (`STARS`, `TERRAIN_3D`) are just below it.

## What's shown under a photograph

**Only the technical line: camera, lens, aperture, shutter, ISO.** No title,
no filename, no date, no location. This is deliberate — do not add them back
without being asked.

Dates appear **once per collection**, under the gallery heading ("December
2025"), never on individual photographs. That line is derived from the capture
dates in the manifest by `collectionDate()` in `site.js`, so it stays correct
as photographs are added. Set `"date"` on a collection in
`data/collections.json` to override it with fixed text — Galápagos, Ecuador,
Malaysia, Arizona, Yunnan and Sri Lanka do, since their files carry no capture dates, and so does any page
that spans separate trips ("January 2024, December 2025"), which the derived
range would misreport — or to `""` to show no date at all.

The order of `data/collections.json` is the order of the home page: **oldest
trip first, by each collection's earliest date**. A new collection goes in by
that rule. Only collections with photographs are listed — there are no
"coming soon" placeholders.

Two switches at the top of `assets/site.js` control all of this:

```js
var CAPTIONS = {
  grid:     { title: false, location: false },
  lightbox: { title: false, location: false, date: false, exif: true }
};

var EXIF_FIELDS = ["camera", "lens", "aperture", "shutter", "iso"];
```

Flip a `CAPTIONS` field to `true` and that line reappears immediately — no
rebuild, no re-import. `grid` is the caption over a thumbnail on hover;
`lightbox` is the block under the enlarged photograph.

`EXIF_FIELDS` sets which technical values print and in what order. Missing
values are skipped, which is why drone frames show fewer items — their
reported "lens" is a bare spec that just repeats the aperture, so `build.py`
drops it.

**No photo counts anywhere.** Not on collection cards, not in headings, not
"19 photos" or "coming soon". A collection is a body of work, not a tally.
This applies to anything added later too.

Related: the photographs keep their **original camera filenames**
(`0Z9A0369.jpg`, `DJI-20251228080241-0076-D.jpg`). Do not invent titles for
them. The `Title_Location_Date.jpg` convention that `build.py` parses is
available if Newton ever wants it, but it is his to use, not yours.

Collection `subtitle` and `blurb` in `data/collections.json` start empty for the
same reason — they're his words to write. When he sends one, put it in as he
wrote it: fix only plain typos, and tell him each change. A blurb can have
several paragraphs; separate them with a blank line (`\n\n`), which the page
shows as the gap (`white-space: pre-line`) and edit mode keeps on save.

## The gallery layout (packed grid)

Collection pages open with a full-width photograph, then a text rail
on the left and packed photo blocks on the right.

`composeBlocks()` in `site.js` walks the collection **in the order photos.json
gives it**. Sequence is controlled entirely by the manifest order — the layout
only decides arrangement, never order.

Arrangement comes from one of two places:

- **An explicit plan.** A collection may carry `"layout"` in
  `data/collections.json`: an array of template names, one per row, applied to
  the photographs in manifest order once the opener has been lifted out. Alaska
  has one. This is how a gallery gets an arrangement that was designed rather
  than improvised.
- **The packer.** With no plan — or once a plan runs out — `pickBlock()` takes
  each position and picks the best template whose cells match the orientations
  coming up.

A plan is a suggestion, never a requirement. The moment a row asks for a shape
the photographs no longer have, because one was added, removed or moved, the
plan is abandoned **from that row on** and the packer finishes the page. So a
stale plan quietly degrades to an automatic layout instead of breaking. If you
reorder a collection that has a plan, expect to rewrite the plan with it.

**Reorder a gallery by reordering `data/photos.json`.** `build.py` preserves
the position of anything already in the manifest and appends newly imported
photographs at the end (newest first) to be placed by hand. It does not
re-sort, because that would silently undo an arrangement.

Photographs are classified from `width`/`height`: `W` panorama (ratio ≥ 2.2),
`P` upright (≤ 0.92), `L` landscape between. A cell marked `*` takes either an
upright or a landscape and crops it square. **Cropping never crosses the
divide** — a landscape never becomes an upright.

A cropped cell trims evenly from both ends. When that would cut something that
matters — a long tail's tip in a 2:3 upright squeezed to 0.74 — give the
photograph `"focus"` in `photos.json`: any CSS `object-position`, such as
`"center bottom"`. `build.py` preserves it like the other hand-edited fields.

**Every template fills the width of the grid**, whether it holds one photograph
or three, so the right-hand edge of the page runs straight the whole way down.
Don't add one that doesn't. A column may carry `nat` instead of `ar`, keeping
that photograph's own ratio rather than cropping it — that is what lets a
panorama run full width at its real 2.70 rather than being trimmed to fit.

`SSSS` is the one template meant for a run of frames rather than a mix: four
squares across, read left to right as a sequence (Colorado & Nebraska's
sage-grouse display). The packer never picks it — put it in a plan — and on a
phone it folds into two rows of two.

`PLLL` is for a collection's one great upright (The Desert West's Arches
frame): 64% wide and uncropped, three landscapes stacked beside it. That is as
big as an upright can be and still be seen whole on a laptop. Plan only; on a
phone it folds to the upright at full width with the three below.

The `n` templates (`PLLn`, `LLPn`, `LPn`, `PLn`, `PPn`) crop nothing, for
a collection shot as 4:5 uprights and 3:2 landscapes; Yunnan and Sri Lanka use
them because Newton asked that Yunnan's landscapes keep their ratio. A `PPn`
of two 2:3 uprights is also uncropped, since both columns share one ratio. The landscapes anchor at
their own shape and the upright stretches beside them. The column widths
(52/48, 65.2/34.8) are solved so that the stretch lands on exactly 4:5 at
laptop size; on a phone only the upright gives up a percent or two. Together
with `L` and `LLe`, which never crop a 3:2 frame, they make a plan with no
cropped cell. They are plan only, and only exact for 4:5 uprights.

`J2` and `J3` crop nothing whatever the shapes, for a collection that mixes
vertical xPans (0.37), 2:3, 3:4, 3:2 and 2.7 panoramas (Alberta, British
Columbia, Yukon). Their columns carry no widths: each grows by its
photograph's own aspect ratio, so every frame keeps its ratio and the row is
one height at any window width, phone included. Their `need` is `?`, which
takes any shape. Plan only. `aspectOf()` clamps ratios to 0.3–4 so that a
vertical xPan is not squeezed; at the old 0.4 floor it was cropped by 8%.

**Saved layouts.** When Newton wants a way back to a gallery's arrangement
before it is redone, tag the commit that has it: `<slug>-layout-<n>`, annotated,
pushed. A layout is two things: the collection's order in `data/photos.json`
and its entry (`layout`, `opener`) in `data/collections.json`. To restore one,
copy just those from the tag, e.g. `git show alberta-bc-yukon-layout-1:data/photos.json`,
and leave every other collection as it is now. **Never `git checkout` or
`git switch` to a tag or commit from before the move to R2** (all the tags
above). Those commits still track `images/`. Checking one out overwrites the
local photographs with old versions, and coming back deletes them from disk.
Read files out of it with `git show` only. A photograph added or removed
since then has to be placed by hand. Saved so far:
`alberta-bc-yukon-layout-1` (the first arrangement, with small vertical xPans) and `alberta-bc-yukon-layout-2` (large vertical xPans, opening on the car at the lake); `peru-layout-1` (the first Peru arrangement, before the swimming caiman moved up to lead full width).

Rows are flush at any window width because exactly one cell per row (the
anchor) carries an `aspect-ratio` and every other cell stretches to the height
it sets. There is no measurement and no resize handler; don't add one.

Columns use `flex: <share> 1 0` — grow from a zero basis, **not** a percentage
basis. Shares sum to 100, so percentages plus the gap would overflow the row
by one gutter and leave a ragged right edge.

Templates carry an optional `pri`, and `pickBlock()` prefers the highest that
fits, using the rotation only to break ties. Upright-led blocks are `pri: 2`
so a portrait gets the dominant cell rather than being squeezed beside a
landscape; the square-cropping block is `pri: -1` because it discards the most
of a photograph.

The opener is the photograph flagged `"featured": true` in `photos.json`,
falling back to the first. Note that `featured` is also
what the home page picks its hero from, so a collection usually wants to be
first in the manifest rather than flagged.

A landscape opener is **full bleed**: always the width of the window. Where
that would make it taller than the window (`--opener-h`, 100vh), it is trimmed
top and bottom rather than shrunk — around its `focus` if it has one, which is
how Malaysia's owl keeps its feet. A panorama never reaches the cap, so it is
never cut; a 3:2 frame on a wide window loses up to about a fifth of its
height; a near-square frame would lose far more, so it makes a poor opener.
An upright opener is not bled: it stays centred, capped at 88vh, uncropped.

A subject that fills its frame top to bottom can't survive that trim — the
Galápagos pelican runs from 6% to 85% of its height, so one screen would cost
it either the crown (under the bar) or the bill tip. Give the collection
`"opener": "whole"` in `collections.json` and its opener is shown entire
instead: still full width, but at its own height, starting below the bar and
running past the fold.

The one place a row can be narrower than the grid is the fallback for a lone
upright the packer couldn't pair off: full width would make it taller than the
window, so it stays centred at 34%. A plan should avoid ever leaving one.

`--book-gap` on `.grid.book` sets the gutter.

## Sizes on the page

Originals are imported at a **4000px long edge, JPEG quality 85**, which is
enough that a full-width photograph on a 5K display is drawn from real pixels.
That is far more than a phone should ever download, so `build.py` also writes
each photograph out at the long edges in `VARIANT_LONG_EDGES` — 800, 1600,
2400 — under `images/_thumbs/<edge>/<slug>/`, and records the whole ladder as
`variants` on the photograph in `photos.json`. The original is always offered
as the largest rung. Nothing is ever upscaled: a variant wider than its source
is skipped.

`variants[].w` is the **real pixel width of that file**, not the long edge — an
upright at a 1600px long edge is 1280 wide, and a `w` descriptor that lied
about it would make the browser choose badly.

In `site.js`, **`responsive()` is the only place a photograph's `src` is
assigned.** It exists because the order is easy to get wrong and fails
silently: assigning `src` first starts a fetch immediately, and the browser
keeps that file and ignores a `srcset` added afterwards. `sizes`, then
`srcset`, then `src`.

**Every caller must state its own `sizes`.** With no `sizes` the browser
assumes the slot is the full viewport and takes the largest rung — the 4000px
original, on a phone, for a thumbnail. Two helpers cover the cases:

- `tileSizes(share)` — `share` is the tile's fraction of the packed grid,
  which is the whole page below 1000px and the 62% right-hand column above it
  (`.book-body`), capped once `--wrap-wide` stops growing at 108rem.
  Callers pass `spec.w / 100` from the block template.
- `cappedSizes(photo, vh)` — for slots limited by window *height* rather than
  width (an upright opener at 88vh, the lightbox at ~80vh). Their width follows
  from the photograph's own ratio, so the hint is `min(100vw, <vh×ratio>vh)`.
  A landscape opener is always the window's width, so it simply says `100vw`.

If a `sizes` hint drifts out of step with the CSS, nothing breaks visibly —
the browser just fetches a file that is too small (soft) or too large (slow).
Change one and check the other.

Two things are outside this system and must be maintained by hand: the **hero**
on the home page is a CSS `background-image`, which cannot carry a srcset, so
`pickForWidth()` chooses a rung once at load; and the **About band** is written
directly into `about.html`, srcset, `width` and `height` included.

A note on the budget: a photograph costs about 2.5 MB with its three smaller
widths. That is why they left git (next section).

## Where the photographs live

**In Cloudflare R2, not in git.** GitHub Pages refuses a site over 1 GB, and
the photographs reached that in October 2026 (Peru). Since then:

- **The bucket** is `newton-liu-photos` on Newton's own Cloudflare account
  (free tier: 10 GB stored, no charge for visitors' downloads; about 1 GB
  used at the move). Each file's key is its repo path, so
  `images/peru/EZLE2124.jpg` in the repo is `images/peru/EZLE2124.jpg` in R2.
- **The address** is the `R2` constant in `assets/site.js`, the one place it is
  written; `upload.py` reads it from there. It is R2's `pub-….r2.dev` address
  for now, which Cloudflare rate-limits and labels for development. The plan is
  a custom domain (`photos.<his domain>`) connected to the bucket in
  Cloudflare, then that one constant changes. Newton is choosing the domain.
- **The live site reads R2; the local preview reads `images/` on disk** (any
  page on localhost/127.0.0.1), so a collection can be arranged before
  anything is uploaded. To preview against R2 instead, run
  `localStorage.media = "r2"` in the console, and delete it afterwards.
- **`images/` is gitignored** except `images/_about/`. The folder on this Mac
  is the working copy; the masters stay in Lightroom; R2 holds the published
  copies. Git history before the move still contains the photographs. Never
  rewrite history to remove them.
- **`tools/upload.py`** uploads exactly what the site asks for (`data/photos.json`,
  plus any `cover` in `data/collections.json`) and is missing from R2. "In R2" means R2's ETag equals the local file's MD5.
  Files that pass are remembered in `.r2-uploaded.json` (gitignored), so
  re-runs only ask about new or changed files. It runs the GPS check again
  before anything leaves the machine. `--check` uploads nothing and exits 1 if
  anything is missing. A file missing from `images/` passes `--check` as long
  as R2 has it. `--verify` re-asks R2 about everything. `--download` fetches
  missing files back from R2, which is how a fresh clone or a lost folder gets
  its `images/` back. Filenames containing `# ? % \` are refused, because
  wrangler can't store them under the right key; `import.py`'s names never
  contain them.
- **Uploads go through `wrangler`** (Cloudflare's CLI, via `npx wrangler@4`),
  signed in by Newton with `npx wrangler login`. That is a browser OAuth he
  approves himself. No key or token is ever stored in the repo or handled by
  you. Only if upload.py says wrangler is *signed out* do you ask him to run
  that. Any other wrangler error is printed as wrangler gave it; a network
  problem is not a sign-in problem.
- **`build.py` won't drop a photograph whose file is missing** unless given
  `--allow-removals`. Without git holding the files, a missing folder would
  otherwise silently remove a collection from the site. To remove a
  photograph on purpose: delete its file from `images/<slug>/`, then run
  `python3 tools/build.py --allow-removals`. It stays in R2 (see below).
- **The hooks** in `tools/hooks/` only run where they are enabled, and that
  setting is per clone: `git config core.hooksPath tools/hooks`. Check it
  with `git config --get core.hooksPath` before relying on them. Worktrees of
  this clone share it. `pre-commit` refuses image files outside
  `images/_about/`, refuses GPS in `images/_about/`, and refuses a staged
  `data/photos.json` or `data/collections.json` that points at files R2
  doesn't have (`upload.py --check` on the staged versions).
  `pre-merge-commit` runs the same checks on a merge. A rebase or
  cherry-pick runs neither, so run `upload.py --check` after one.
- **On a new machine or a fresh clone**: `git config core.hooksPath tools/hooks`,
  then `python3 tools/upload.py --download` to bring back `images/`. Newton
  runs `npx wrangler login` before the first upload.
- **Other checkouts and branches from before the move.** The worktree
  `~/newton-liu-globe` (branch `globe`) was started before the move: there
  `images/` is still tracked and its CLAUDE.md is the old one. Merging main
  into such a branch deletes the photographs from *that checkout's disk*.
  That's expected; git is applying the untracking. Copy them back from
  this checkout with `cp -Rc ~/newton-liu.com/images/. images/` (an APFS
  clone: instant, no extra space), or run `upload.py --download` there. Merging such a
  branch into main is safe once the hook is on (the merge hook refuses any
  image it would add), but check `git diff main...<branch> --stat -- images`
  first.
- **Removed photographs stay in R2.** Nothing deletes from the bucket
  automatically. They cost nearly nothing; clean up only on Newton's say.
- Files are served with `Cache-Control: public, max-age=86400`. A photograph
  re-exported under the same name can show its old version for up to a day to
  a browser that already has it.

## Prose pages (About, Contact)

Both use the gallery's vocabulary rather than the old centred `.prose` block: a
sticky left rail carrying the page label and jump links, a right-hand column of
text at a 62ch measure, section headings as hairline-ruled small caps.

The markup is `.about-band` (optional photograph) then `.about-body` >
`.about-rail` + `.about-prose`. `.about-body.is-bare` adds the top padding a
page needs when it has no band — Contact uses it, because two pages opening on
the same photograph looks like a mistake.

The About band is **the one photograph hand-written into HTML**. It is page
furniture, not a collection entry, so it is deliberately outside `photos.json`:
the file and its 800/1600/2400 widths live in `images/_about/`, which the
build skips. Nothing checks that they still exist, so if they are moved or
renamed, change the `src` and `srcset` in `about.html` too.

The older `.prose`/`.prose h1` rules are still in `site.css` but nothing uses
them now. They're the fallback if a plain text page is ever wanted.

## Editing the words (?edit)

**Add `?edit` to any page's URL and the words on it become typeable.** A bar
appears at the top; click any dashed outline and write. Enter starts a new
paragraph; selecting text brings up bold / italic / heading / link. Cmd-S or
the Save button writes it down.

`assets/edit.js` does this, and it also runs on every ordinary page load,
where it does one quieter job: overlaying `data/text.json` onto the page.

**`data/text.json` is every word on the site that isn't a photograph's own
data.** The HTML still carries the copy as its default; a key in text.json
overrides it. So:

- Editing a page in the browser writes text.json, not the HTML.
- **If you change copy in an HTML file and the page ignores you, the key is
  in text.json.** Change it there, or delete the key to hand the slot back to
  the HTML. This is the one surprising thing in the repo.
- text.json is a plain file. Editing it by hand is exactly as valid as using
  ?edit — same destination.

An element joins the system by getting a `data-edit="<key>"` attribute:

```html
<p class="hero-sub" data-edit="home.heroSub">…</p>          <!-- one line -->
<div class="about-prose" data-edit="about.prose" data-edit-rich>…</div>
<h1 class="hero-title" data-edit="home.heroTitle" data-edit-lines>…</h1>
```

`data-edit-rich` means a block of prose — paragraphs, headings, lists — stored
as HTML and put through a sanitiser that keeps `p h2 h3 br em strong i b a ul
ol li blockquote` and the attributes `id class rel href`, and drops everything
else. `data-edit-lines` means the line breaks typed into it are meaningful
(the hero title's break). Plain `data-edit` is one line of text with its
whitespace collapsed. `data-edit-hint` is the grey prompt shown when a slot is
empty — without one, an empty slot has no height and can't be clicked.

Collection titles, subtitles and blurbs are editable the same way on a gallery
page, but they save to **`data/collections.json`**, which stays their home;
edit.js wires those three up by selector, so the generated stubs need no
attributes. Only the file that actually changed gets written.

A prose page's jump links are **rebuilt from the headings that are really in
its prose**, so rewriting a page can't leave the rail pointing at anchors that
no longer exist. The nav opts in with `data-jump-from=".about-prose"`; links
in it that point somewhere other than `#` are kept, and kept last.

### Publishing an edit

With no token, Save downloads the changed files for you to put back in the
repo and commit. Paste a GitHub token into the ⚙ panel and Save commits
straight to `main` instead, and Pages redeploys in about a minute.

The token is a **fine-grained personal access token, scoped to this repository
alone, with Contents: Read and write** — nothing else. It lives in that
browser's localStorage and never in the repo. It is worth being clear-eyed
about the trade: anyone with that browser can publish to the site. It is not
worth pasting on a shared machine, and `REPO`/`BRANCH` at the top of edit.js
are the only things that decide where it writes.

Nothing in edit mode is visible to a visitor. `?edit` on the live site would
let a stranger type into their own copy of the page and change nothing —
saving needs the token, and they don't have it.

## Conventions

- **No build step.** No npm, no bundler, no framework. What you edit is what
  ships. Keep it that way — it is the reason this site is easy to work on.
- **Relative paths only** (`assets/site.css`, not `/assets/site.css`). The
  GitHub Pages preview URL serves from a subpath and absolute paths break there.
- **All design tokens live in the `:root` block** at the top of
  `assets/site.css`. Restyling should mostly mean editing that block. If a
  colour or size is hard-coded further down the file, that is a bug worth fixing.
- **Two grounds: black (default) and gray.** The square at the end of the
  nav (added by site.js) switches to the gray palette in
  `:root[data-theme="dark"]` and remembers the choice per visitor in
  localStorage; "dark" in the code means gray. White was retired with the
  globe. The landing itself is always the near-black of space. A colour
  token added to `:root` needs a gray value
  there too. Every page's `<head>` carries a one-line script that applies a
  saved gray before the first paint (no white flash); the collection pages get
  it from `PAGE_TEMPLATE` in build.py, where its braces are doubled for
  `.format()`.
- **Vanilla JS, no libraries** — except MapLibre on the globe page (see
  "The globe"). ES5-ish syntax, no transpiling.
- **Filenames stay as the camera wrote them** (see "What's shown under a
  photograph"). `build.py` *can* parse `Title_Location_YYYY-MM-DD.jpg` and
  falls back to EXIF for the date, but that convention is Newton's to use.

## Adding photographs

```bash
# Export from Lightroom at any size — import.py handles the downscaling.
python3 tools/import.py ~/Desktop/"2025.12 West JPEG" --collection west
# A new collection also needs its entry in data/collections.json (slug =
# the folder name, title, date line, place in the oldest-first order).
python3 tools/build.py
python3 tools/serve.py          # preview at localhost:8137 (reads images/ on disk)
python3 tools/upload.py         # photographs to R2; GPS-checked again
git add -A && git commit -m "Add Yunnan 2025" && git push
```

`git add -A` is safe: `images/` is gitignored, so only the data and pages are
committed. If the hooks are enabled (see "Where the photographs live"), the
commit is refused when `upload.py` hasn't been run.

`import.py` resizes to a 4000px long edge (never enlarging a smaller file), reads only from the
source folder, and **refuses to import anything carrying GPS coordinates**
unless you pass `--strip-exif` or `--allow-gps`. Use `--dry-run` first when
unsure. It is the reason masters never end up in the repo — always import
through it rather than copying files into `images/` by hand.

`build.py` never overwrites hand-authored text (`title`, `location`, `date`,
`caption`, `collection`). It only refreshes mechanical fields — dimensions,
EXIF, thumbnail paths. To re-derive a field, delete it from `photos.json` and
rebuild.

## Things to be careful about

- **Never commit full-resolution originals.** Git keeps them forever, and the
  repo has a 1 GB soft limit. Web-sized exports only; masters stay in
  Lightroom. `.gitignore` blocks RAW and TIFF extensions as a backstop.
- **Don't commit photographs at all** (except `images/_about/`). They go to
  R2 through `upload.py`; `.gitignore` and the pre-commit hook back this up.
- **EXIF GPS is not stripped by this project.** Strip it at export time.
  Precise coordinates for nests, roosts and rarities should not be published.
  `import.py` and `upload.py` both refuse a file that carries it.
- **This repo is public.** Everything pushed is permanent and world-readable,
  including anything later deleted.
